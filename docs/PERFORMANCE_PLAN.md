# План улучшения производительности Tessery

Дата: 2026-09-12. Исходная ревизия: `368d00ad78af19ecd5c8b3f3721cd6532b07a62f`.
Это план будущих работ, а не результаты новых экспериментов. Текущий многочасовой
прогон использует отдельный неизменяемый снимок. Новые GPU-измерения следует начинать
после его завершения; новые модели для первых этапов не нужны.

**На что опирается план.** В актуальном [отчёте](BATCHED_FUSED_MLP.md) смешанный
Qwen-батч `[3,7,10]` имеет задержку на 10–12% выше MLX, `4×33` — на 40–41%,
512 токенов — на 55–57%. На семи токенах Tessery быстрее, на 24 — примерно паритет.
Это локальная M1-выборка, не общий рейтинг движков. Два из шести BGE timing-сценариев
не прошли проверку шума. Нельзя выбирать оптимизацию по их относительной скорости.

У смешанного батча после fusion остаются 1070 dispatches и около 12 мс command
encoding. Этот счётчик включает Python, driver и работу внутри command(), в том
числе allocations; все 12 мс нельзя приписывать только ctypes. Для `4×33` GPU-время
около 170 мс при encoding около 5 мс: устранение Python overhead не закроет весь
разрыв длинных запросов. GPU-время входит в submit/wait и не суммируется с ним.

В текущем коде уже есть единый command buffer на forward, pipeline cache,
ограниченный scratch cache, batching по длинам, tiled attention и quantized GEMM.
Эти механизмы нужно улучшать, а не заново предлагать их внедрение. Исторические
профили до последних fusion и смены тайлов требуют обновления. Эксперимент только
с перестановкой обхода тайлов не дал устойчивой пользы на целевых длинных формах:
см. [результаты](QUANTIZED_TRAVERSAL.md).

**Порядок работ.**

| Этап | Работа | Первый ограниченный эксперимент | Условие продолжения |
|---|---|---|---|
| 0 | Завершить квалификацию и обновить профиль | Короткие, смешанные и длинные входы; обычные timings отдельно от GPU capture | Воспроизводимый источник затрат и корректная baseline |
| 1 | Уменьшить CPU-подготовку | Выполнение заранее подготовленного списка операций через один C ABI вызов | Снижение полного encode(), прежде всего коротких батчей |
| 2 | Точечные слияния | BGE matmul+bias; затем Qwen residual+RMSNorm и Q/K norm+RoPE | Те же численные проверки, меньше dispatches и/или GPU-времени |
| 3 | Улучшить матричные kernels | M24/K64, несколько вариантов размеров тайла для M128–512, отдельные small-M пути | Повторяемый выигрыш на нескольких реальных слоях и в encode() |
| 4 | Улучшить существующий attention | Изменить распределение работы и переиспользование K/V, один вариант за раз | Польза на 128–512 токенах без ухудшения коротких |
| 5 | Повысить скорость индексации и поиска | Повторное использование tokenization, нормы индекса и частичный top-k | Выигрыш измеряется отдельно для build/search и нагрузки очереди |

**Этап 0 — измерительная база.** Завершить уже запущенные 2 часа Qwen, 2 часа BGE
и 4 часа Kaggle CPU; результаты относятся только к их зафиксированной ревизии.
После этого снять новый профиль семейств операций на текущих kernels: GEMM,
attention, normalization, RoPE, CPU tokenization, encoding, allocations/readback.
Существующий profile_kernels() на M1 меняет границы encoders и влияет на скорость:
он локализует затраты, но не заменяет обычный benchmark.

Сохранить нынешнюю MLX baseline для сравнения с историей и добавить отдельную
скомпилированную чистую модельную функцию через `mx.compile`. Динамические lengths
и masks должны оставаться входами; загрузка, tokenizer и Python-проверки вне
компилируемой части. Измерять cold compile отдельно, исключить повторную компиляцию
из steady-state. Не предполагать, что весь текущий wrapper компилируется напрямую.
MLX документирует слияние операций и особенности повторной компиляции при изменении
форм: [официальное руководство](https://ml-explore.github.io/mlx/build/html/usage/compile.html).

Сравнивать отдельно backend и публичный encode(): нынешние окружения имеют разные
версии regex, поэтому одинаковые token IDs ещё не устраняют tokenizer timing
confound. Для backend использовать одинаковые готовые IDs; для нового API-сравнения
по возможности выровнять зависимости в изолированном окружении. Отдельно сохранить
тест общего batching-плана и, позднее, настройки, выгодные каждому движку.

**Этап 1 — подготовленный native execution plan.** Сейчас `_dispatch` собирает
Params и ctypes pointers, передаёт имя kernel, а native делает строковый lookup
pipeline и bind каждого buffer. Сначала разрешать kernel handles и постоянные
weight bindings один раз; затем передавать список операций в Objective-C++ одним
вызовом на forward. GPU-kernels, их порядок и арифметика на первом эксперименте
остаются прежними — так можно выделить эффект host orchestration.

Ключ плана должен учитывать модель, device, shader/ABI, execution shape, dtype и
выходную размерность. Динамические входы и lengths обновляются на каждом запросе.
Ссылки на workspace нельзя переживать его освобождение: trim, close, смена buffers
и модели должны инвалидировать соответствующие планы. Нужны ограничения числа
планов и памяти, учёт native-ресурсов, сохранение admission/cancellation/error
semantics. Один план сначала покрывает `[3,7,10]`; затем добавляются контрольные
формы и изменения порядка запросов.

Оценка масштаба, не прогноз: уменьшение 12 мс encoding вдвое даёт около 6 мс
экономии, а не двукратное ускорение всей модели. Этот этап приоритетен для коротких
запросов, но для длинных основная работа остаётся на GPU.

**Этап 2 — слияния с локальными зависимостями.** В BGE каждый linear всё ещё
завершается отдельным add_bias. Начать с bias в epilogue matmul; следующий вариант
добавляет текущий erf-GELU к intermediate projection. Не заменять его tanh-GELU.
После этого проверить residual+LayerNorm, сохраняя округление суммы и нормализации.

В Qwen проверить residual+RMSNorm с сохранением обоих нужных результатов, затем
Q/K RMSNorm+RoPE. Альтернативный маленький эксперимент — кэш частот или sin/cos для
заданных theta, head_dim и позиций с явной проверкой численного совпадения. Эти
альтернативы измерять по отдельности. Полный fused transformer block пока не нужен:
между некоторыми операциями требуется синхронизация разных threadgroups.

Объединение QKV — отдельный более сложный вариант: три quantized набора наивно
не помещаются в нынешние восемь buffer bindings. Нужны offsets/packed bindings
или иной ABI; не следует копировать все веса на каждом вызове ради fusion.

**Этап 3 — quantized GEMM и специализация форм.** Самый небольшой следующий
эксперимент: восьмирядный fused хвост M24 с декодированием полного K64 вместо K32,
сохраняя независимые K32 partial sums. Проверить экономию metadata loads/barriers
против роста threadgroup memory; действующий вариант остаётся baseline.

Для M128–512 сравнить небольшую сетку тайлов: 16×64 и 32×32 против текущего 16×32,
а также staging двух K-блоков, если счётчики подтверждают ожидание памяти. Большой
тайл может снизить occupancy из-за registers/shared memory. Не менять все параметры
сразу. Apple рекомендует сопоставлять occupancy с limiter/cache/bandwidth counters,
а не максимизировать occupancy как самостоятельную цель:
[документация GPU occupancy](https://developer.apple.com/documentation/xcode/finding-your-metal-apps-gpu-occupancy).

Использовать реальные активации и веса раннего, среднего и позднего слоя плюс
синтетические cancellation/saturation patterns. Отдельно проверить small-M=1/2/4,
переиспользование packed words между несколькими output channels и стоимость хвостов.
Расширять guards fused MLP на соседние высоты только после full-model сравнения.
Подбор вести офлайн, сохранять небольшую таблицу проверенных правил для GPU family;
не запускать большой autotuner при каждом старте приложения.

**Этап 4 — attention следующего варианта.** Tiled online-softmax уже реализован.
Новые гипотезы: другой размер query/key tiles, меньше обменов через threadgroup
memory, double buffering K/V и более выгодное распределение matrix/non-matrix
операций. Для Qwen конфигурация 16 query heads / 8 KV heads позволяет отдельно
исследовать переиспользование K/V между парой query heads; эффект зависит от cache
и роста состояния threadgroup.

Split-KV имеет смысл только при недостаточном параллелизме: он добавляет partial
buffer, reduction и меняет порядок суммирования. На текущем лимите 512 токенов
накладные расходы могут перевесить пользу. Слияние partial softmax требует
устойчивого объединения max, denominator и numerator; усреднение готовых attention
outputs неверно. Источник алгоритмических идей —
[FlashAttention-2](https://arxiv.org/abs/2307.08691); ускорения на NVIDIA из статьи
не являются прогнозом для Apple M1.

**Этап 5 — RAG и throughput.** В index builder текст токенизируется при подборе
chunk, затем снова внутри encode. Проверить внутренний prepared-input путь с
сохранением проверки модели, truncation и отмены. Публичный API не обязан принимать
непроверенные IDs. Для неизменяемого DocumentIndex можно один раз проверять/кэшировать
нормы документов; общая cosine_search должна сохранять поддержку произвольных
конечных векторов и устойчивость к overflow/underflow.

Полный stable sort заменить частичным top-k только с корректным разрешением ties
на границе k по исходному индексу. Это низкорисковая CPU-гипотеза, не доказанный
главный bottleneck. GPU exact search имеет смысл лишь после измерения crossover
размера корпуса/числа запросов; при текущем лимите 10 тысяч chunks CPU может быть
быстрее с учётом запуска GPU. ANN потребует отдельного контракта качества поиска.

Для массовой индексации исследовать подготовку следующего батча во время GPU-работы
и ограниченное объединение ожидающих запросов. Первый прототип сохраняет единственный
GPU-forward и не увеличивает число simultaneously-live workspaces. Нужны FIFO,
backpressure, cancellation и явный предел ожидания; рост texts/s не должен выдаваться
за снижение latency одиночного запроса.

**Отдельные экспериментальные ветки.**

| Вариант | Почему может помочь | Основное ограничение |
|---|---|---|
| Повторное исполнение через Metal ICB | Сохранить подготовленные команды и уменьшить повторный driver encoding | Только после native-plan; проверить compute support, зависимости/barriers, resource residency, lifetime и инвалидирование |
| Последний слой только для pooled query | Последний валидный токен Qwen / CLS BGE — единственный выход документа | K/V всех valid tokens всё ещё нужны; сохранить позиции, masks и полную hidden-нормализацию |
| FP16 operands с F32 accumulation | Меньше трафик активаций и потенциально более выгодные матричные операции | Не гарантирует ускорение, меняет результаты; отдельный явный precision profile и quality evaluation |
| Ограниченный weight prepack | Удобнее совместные bindings, tile layout и reuse | Учесть cold cost и пиковую память; не создавать постоянную F32-копию всей uint4-модели |
| Arena и aliasing scratch по времени жизни | Снизить allocation churn и ненужный up scratch на fused-only пути | Проверить все fallback формы, trim/cancel/close; нельзя повторно использовать память до completion |

Apple описывает ICB как сохраняемые для повторного исполнения команды; это
возможность платформы, а не гарантия ускорения нашего графа. Начать с двух зависимых
compute kernels, затем одного слоя. Обычный уже выполненный command buffer
переиспользовать нельзя:
[ICB](https://developer.apple.com/documentation/metal/creating-an-indirect-command-buffer),
[CPU encoding](https://developer.apple.com/documentation/metal/encoding-indirect-command-buffers-on-the-cpu).

Специализация последнего слоя — вывод из проверенных зависимостей нашего forward,
пока без прототипа. Все предыдущие слои остаются полными; в последнем нужны K/V
всего текста, а Q/attention output/MLP можно попробовать считать лишь для выбранного
токена. Верхняя оценка при одинаковой стоимости слоёв — меньше 1/28 работы Qwen
или 1/12 BGE (примерно 3,6%/8,3%); реально часть последнего слоя остаётся, а малые
матрицы могут исполняться менее эффективно. Это не обещание такого ускорения.

FP16-ветка не проходит в нынешний профиль путём ослабления tolerances. Её следует
оценивать отдельно: ошибки векторов, cosine drift, Recall@k/MRR на зафиксированном
небольшом корпусе, нормализация, masks и крайние входы. F32 accumulation само по
себе не отменяет ошибки округления входов. У uint4 packed weights размер не
уменьшится вдвое только от FP16 активаций. Начать с имеющихся весов, без загрузки
новых больших моделей.

**Как принимать решения.** Каждый опыт — одна гипотеза, отдельный переключатель,
старый fallback, небольшой prototyping budget. Сначала microbenchmark, затем
публичный encode(); локальное ускорение kernel без пользы для запроса не является
достаточным основанием усложнять production.

Матрица должна включать `[3]`, `[7]`, `[17]`, `[24]`, `[3,7,10]` и перестановки,
`4×33`, 128/159/160/161/256/512, соседние границы тайлов и ragged/Unicode inputs.
Фиксировать execution plans, token IDs, модель, shader/bridge hashes, cold/warm,
p50/p95, CPU/GPU timing, allocations, RSS, cache и число dispatches. Повторять
сравнение в свежих процессах и обратном порядке, с одинаковыми baseline A/B.

Существующие ±10% A/B и ≤15% process drift — фильтр грубого шума, недостаточный
для доказательства малого выигрыша. Для эффекта порядка 3–5% нужны дополнительные
повторы и интервал неопределённости парных разностей с учётом блоков измерений;
не принимать эффект, неотличимый от шума. Заранее выбрать целевые сценарии и предел
регрессии контрольных случаев, отдельно оценивать latency и throughput.

Для существующего precision profile сохраняются kernel F64 gates и embedding
`atol=5e-6, rtol=1e-4`, при сохранении порядка операций — exact equality со старым
путём. Обязательны Shader Validation, границы buffers, отмена, overload, trim,
close/reload и проверка собранного wheel. Не расширять по умолчанию cache64MiB,
не скрывать память планов/ICB вне accounting. Многочасовую квалификацию повторять
на выбранной итоговой ревизии, а не после каждого отклонённого микропрототипа.

Первые три практических опыта после baseline: **native execution plan → BGE
matmul+bias → Qwen residual+RMSNorm**. Затем выбрать между GEMM и attention по
обновлённому профилю. ICB и pooled-query final layer — наиболее интересные
экспериментальные продолжения; FP16 остаётся отдельной веткой качества/скорости.
